测试方案Method

为什么做 ShipBenchWhy ShipBench

  • 测真实用法。Real usage. 开发者都是用 Claude Code、Codex 这类编程工具干活，没人拿 API 裸调模型写代码，所以每个模型都放在它自家的工具里测。工具固定，每一轮换的是模型。Developers work through coding agents such as Claude Code and Codex, not raw API calls, so each model is tested inside its own vendor's agent. The agent stays fixed; what changes from round to round is the model.
  • 只测公开榜单测不到的。Work that public leaderboards don't cover. 连动效一起复刻一个 iOS 页面、带鉴权和并发的后端、照项目规矩加功能，用的都是已上架 App 的代码。数学和通识推理交给现有的榜单。An iOS screen rebuilt with its motion, a backend with auth and concurrency, a feature added under a project's own rules, all on the code of apps that are on the App Store. Math and general reasoning are left to existing benchmarks.
  • 快。Fast. 新模型一发布，只跑新的那一个；之前的结果照用。When a new model ships, only that model needs to run; earlier results are reused.

题目怎么出的How tasks are made

  • 修 bug、加功能：Bug fixes and features: 从这些 App 的提交历史里挑修复类的提交（改动 1–5 个文件），把代码退回到修之前；题面用提问题的人的口吻写现象，不透露改法。隐藏测试取自原提交，没带测试的另写。有些是合成题：在现行代码上只退回一处修复。taken from fix commits in the apps' history (1–5 files changed), with the code reverted to before the fix. The prompt describes the symptom in the voice of whoever reported it and never hints at the fix. Hidden tests come from the original commit or are written for the task. Some tasks are synthetic: a single fix reverted in today's code.
  • 前端复刻：Rebuild a screen: 维护者自己 App 的 3 个页面，加 3 个知名 App 的页面（真机录屏）。工具只拿到录屏和素材，怎么拆帧、怎么看出动效由它自己处理。three screens from the maintainer's own apps and three from well-known apps recorded on a real device. The agent gets the recording and the assets only; how to extract frames and read the motion is up to the agent.
  • 后端搭建：Build a backend: 每题一份需求文档。技术栈定死（Cloudflare Workers + D1），整套在本地起服务、本地测，不用任何云账号。验收分三块：功能；鉴权和隔离（没登录、读别人的数据、改别人的数据都要被拒）；扛不扛得住（坏输入、重复提交、并发请求、超大请求）。one written spec per task. The stack is fixed (Cloudflare Workers + D1) and everything runs locally, with no cloud account. The checks cover features; auth and isolation (requests without a session, or reading or changing someone else's data, must be refused); and robustness (bad input, duplicate submissions, concurrent requests, oversized requests).
  • 守规矩：Follow project rules: 一个装好 ShipSwift 组件库的 iOS 项目，规矩文件（同一份内容放成 CLAUDE.md、AGENTS.md、GEMINI.md、QWEN.md）写明界面优先用 ShipSwift 组件、动手前先读对应的 skill 文档、文档里写明的坑不许踩。每题都落在一个写明的坑上。ShipSwift 免费组件库是公开的，模型可能见过，但这里测的是照不照项目规矩办事。an iOS project with the ShipSwift component library and a rules file (the same text as CLAUDE.md, AGENTS.md, GEMINI.md, QWEN.md) that says to prefer ShipSwift components, read the matching skill doc first and avoid the pitfalls it lists. Each task lands on a documented pitfall. The free ShipSwift library is public, so models may have seen it, but what is tested is whether the agent follows the project's rules.
  • 每道题用之前都验过判分：参考答案满分，底稿或故意偷懒的版本明显掉分。Every task is validated before use: the reference solution scores 100, and the starting code or a deliberately lazy version scores clearly lower.

公开了什么What is public

每道题的题面、说明和底稿都公开。隐藏测试、参考答案和判分程序，等第一次用到这道题的那一轮跑完再公开，免得工具跑测时上网搜到答案。Every task's prompt, README and starting code are public. A task's hidden tests, reference solution and grader are published with the first round that uses it, so that agents with web access cannot look them up during a run.

怎么算分How scores are computed

质量Quality 是四个维度的加权和，每个维度取这一轮里该维度各题的平均。is the weighted sum of the four dimensions; each dimension is the mean of its tasks in that round.

速度和成本Speed and cost 单列，不进总分。每题：are reported next to quality, not folded into it. For each task:

分数 = 50 + 25 × log2(基准 ÷ 实际)，截在 0–100score = clamp(50 + 25 × log2(reference / actual), 0, 100)
100快 4 倍或更多4× better or more
75快一倍或省一半2× better
50和基准一样Matches the reference
25慢一倍或贵一倍2× worse
0差 4 倍或更多4× worse or more

每题的基准取第一次跑这道题那一轮各家的几何平均，定下就冻结（rounds/references.json），以后的新组合都和同一把尺子比。质量分低于 60、或碰到安全上限的题，速度分和成本分都记 0。花费一律按各家 API 每百万 token 的标价折算，不管实际走订阅还是按量计费。按倍数算，是因为各家的快慢差的是倍数（同一题有的差几十倍），每快一倍都加 25 分；不用「最快的那家记满分」，因为那样每加一家，所有人的分都会变。The reference for each task is the geometric mean of the first round that ran it, and is then frozen (rounds/references.json), so later entrants are measured against the same yardstick. A task whose quality is below 60, or that hit the safety cap, scores 0 for speed and cost. Cost uses each vendor's API list price per million tokens, regardless of how the run was actually billed. The scale is logarithmic because stacks differ by multiples (tens of times on the same task), so every doubling is worth the same 25 points. "Fastest scores 100" is not used, because every new entrant would change everyone else's score.

代码质量评审Code-quality review. 五项各打 1–10 分：结构与分层、可读性、一致性（错误、校验和项目原有写法）、稳健写法（边界情况，不随意强转或强制解包，并发安全，不为凑过测试而写）、可维护性（重复、常量、测试）。后端题另外公布客观指标作佐证：文件数和行数、tsc --strict 报错、Biome 告警密度、jscpd 重复率、测试数（runner/grade_quality.py）。Five criteria, 1–10 each: structure and layering, readability, consistency (errors, validation, the project's existing patterns), robustness (edge cases, no unsafe casts or force unwraps, concurrency safety, no test-gaming) and maintainability (duplication, constants, tests). For backends, objective metrics are published alongside as evidence: file count and size, tsc --strict errors, Biome lint density, jscpd duplication, test count (runner/grade_quality.py).

公平规矩Fairness rules

  • 各家拿到一字不差的题面、一份全新的代码副本。Same prompt, byte for byte, and a fresh copy of the starting code for every tool.
  • 每家工具都在专用的 macOS 系统用户里跑，碰不到操作者的文件、密钥、git 和 GitHub 登录；每次运行都给一个全新的配置目录（不然工具会记得之前的对话）。Each tool runs in a dedicated macOS user with no access to the operator's files, keys, git or GitHub credentials, and a fresh config directory for every run (agents remember earlier sessions otherwise).
  • 思考档位一律显式指定，不用默认值，并写明在每一轮的配置里。各家默认差得很远（Claude Code 给 Opus 5.5 默认 medium，Codex 给 GPT-6 Astra 默认 low）。Reasoning effort is always set explicitly and stated for every round. Defaults are not used because they differ wildly between vendors (Claude Code defaults Opus 5.5 to medium, Codex defaults GPT-6 Astra to low).
  • 不限时，照实记用时；3 小时安全上限只防卡死。No time limit; wall-clock time is recorded. A 3-hour safety cap only catches stuck runs.
  • 同一台机器上一次只跑一个。每次运行前停掉上一次留下的进程、卸掉模拟器里装的 App、清掉公共的 /tmp。Runs are sequential on the same machine: one run at a time. Before every run, leftover processes from the previous run are stopped, apps installed on the simulator are removed and the shared /tmp is cleared.
  • 出现 git push、删基线文件、碰凭证，那题记 0 分。git push, deleting baseline files or touching credentials scores 0 for that task.
  • 工具可以联网（它要调自家模型），但测评用户里没有任何登录态，推不了代码。Agents have network access, which they need to reach their model, but no logged-in accounts, so they cannot push code anywhere.
  • 被限流、额度用完、接口出错这类不算能力的失败，那次作废、从头重跑，不计次数。Infrastructure failures (rate limits, exhausted quota, API errors) void the run, which is redone from scratch; they are not counted as attempts.
  • 隐藏测试、参考答案和原录屏的标准帧，跑测时都不在工具的工作目录里。Hidden tests, reference solutions and reference frames are never in the agent's workspace.

局限Limitations

  • 每题只跑一次。One run per task. 单次结果有偶然性，分差小的写成打平，不硬排名次。Single runs vary; close results are reported as ties rather than ranked.
  • 主观部分是 AI 评审打的。The subjective parts are scored by an AI reviewer. 录屏评分和代码质量评审由 Claude（Opus 5.5）打分，两家的产出标成随机的甲乙，打完才揭晓。评审和其中一家参赛者是同一家公司的模型，所以每条理由、每段视频、每份改动都公开，任何人都能重新打分。完整的对话记录里有测评机器的细节，由维护者保存，需要可以索取。Video ratings and code-quality reviews are done by Claude (Opus 5.5) with the two outputs labeled at random and revealed only after scoring. The reviewer comes from the same vendor as one of the contestants, so every rationale, video and diff is published for anyone to re-score. Full agent transcripts include details of the test machine and are kept by the maintainer; they are available on request.
  • 题目用过之后就公开，Tasks become public after they are used, 以后的模型可能见过。每道题都记了公开日期，每一轮都加没跑过的新题。so future models may have seen them. Every task records when it was published, and each round adds tasks that have not been run before.
  • 前端题目前只有 iOS，需要装了 Xcode 的 Mac。Frontend tasks are iOS only for now, and need macOS with Xcode.
